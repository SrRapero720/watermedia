# TODO

Features planned for future 3.x.x releases. Each entry names the gap as it stands today and what closing it involves.

## Future 3.x.x features

- **CanvaAPI: image, audio and video editor.** WATERMeDIA only plays, decodes and encodes media today; nothing lets a mod edit it (cut, crop, resize, mix tracks, layer pictures or apply filters) before playing or exporting it. Closing it adds `CanvaAPI` on top of the codecs and the _FFmpeg_ filters, with its results playing through `PlayerAPI` and exporting through the encoders.
- **Compressed-texture (BCn) uploads in the GL and Vulkan engines.** `PixelFormat` models BC1/BC2/BC3/BC5/BC7 and `BcReader` hands out the blocks of a BC1/BC3/BC7 DDS texture array with their `PixelFormat`, but `GFXEngine.supports` declines every compressed format, so no built-in engine accepts them and no player opens DDS sources (`CodecsAPI.reader` does not dispatch them). The feature uploads the blocks as they come (`glCompressedTexSubImage2D` / `VK_FORMAT_BC*`) so the GPU samples them directly, then routes DDS sources through `BcReader` in the image player.
- **HDR tone mapping from the stream's metadata and on software engines.** The GL and VK engines map PQ and HLG to SDR with a fixed 1000-nit peak and a highlight knee, ignoring the mastering-display and content-light side data (`AVMasteringDisplayMetadata`, `AVContentLightMetadata`) that state the real peak, and the software engines (AWT, JavaFX) receive BGRA from `sws_scale`, which applies the stream's matrix and range but cannot tone map, so HDR looks dim and flat there. Closing it carries the peak in `Colorimetry` and gives the BGRA path a tone-mapping step (libavfilter `tonemap` or a CPU curve).
- **Real WaterMedia version in IDE runs.** `IOTool.jarVersion` reads `Implementation-Version` from the `MANIFEST.MF` of the jar that loaded the class, so the IntelliJ "WaterMedia App" run, which loads `build/classes/java/main` instead of the jar, reports `WaterMedia.VERSION` as "unknown" in the app headers, the startup log and the issue report; the report's Binaries line reads "unknown" too, since the binaries classes compile into that same folder. Closing it gives class-folder runs a version source, either the jar manifest copied next to the classes or a run configuration that launches the built WaterMedia and Binaries jars.
- **Vulkan frame-texture fast path for animated pictures.** `GLEngine` implements `preload`/`frame`, keeping every frame of an animated image as its own texture under `player.watertx.texturesBudget`, while `VKEngine` does not, so on Vulkan `TxMediaPlayer` falls back to decoding and uploading each frame on every repetition. Parity needs one image per frame (or one array image) plus the VRAM gate on the VK side.
